# TCP, Redis ও gRPC —

এই ডকুমেন্টে তিনটি জিনিস আলাদা করে বোঝানো হয়েছে। তিনটা একই লেভেলের জিনিস না, তাই শুরুতেই পার্থক্যটা বুঝে নেওয়া ভালো:

| বিষয় | ধরন | কাজ |
|---|---|---|
| **TCP** | নেটওয়ার্ক প্রোটোকল | দুই কম্পিউটারের মধ্যে নির্ভরযোগ্যভাবে ডেটা পাঠানো |
| **Redis** | ইন-মেমোরি ডেটাবেস / ক্যাশ | খুব দ্রুত ডেটা সংরক্ষণ ও পড়া |
| **gRPC** | RPC ফ্রেমওয়ার্ক | এক সার্ভিস থেকে আরেক সার্ভিসের ফাংশন কল করা |

## ১. TCP (Transmission Control Protocol)

### TCP কী?

TCP হলো ইন্টারনেটের একটি **নির্ভরযোগ্য (reliable) যোগাযোগ নিয়ম**। দুটি ডিভাইস (যেমন তোমার ব্রাউজার আর একটা সার্ভার) যখন ডেটা আদান-প্রদান করে, TCP নিশ্চিত করে যে:

- ডেটা **হারিয়ে যাবে না**
- ডেটা **ঠিক ক্রমে (order)** পৌঁছাবে
- ডেটা **নষ্ট (corrupt) হবে না**

### বাস্তব উদাহরণ

ধরো তুমি ডাকযোগে একটা বই পাঠাচ্ছো, কিন্তু বইটা ১০০ পাতার আলাদা আলাদা খামে যাচ্ছে। TCP হলো এমন একটা নিয়ম যেখানে:

1. প্রতিটি খামে পেজ নম্বর লেখা থাকে
2. প্রাপক প্রতিটি খাম পেয়ে "পেয়েছি" বলে জানায় (acknowledgement)
3. কোনো খাম হারালে প্রেরক আবার পাঠায়
4. প্রাপক সব খাম নম্বর অনুযায়ী সাজিয়ে বই বানায়

### 3-Way Handshake

ডেটা পাঠানোর আগে TCP একটা সংযোগ (connection) তৈরি করে:

```
Client                         Server
  |  ---- SYN ---------------->  |   "আমি কানেক্ট করতে চাই"
  |  <--- SYN-ACK -------------  |   "ঠিক আছে, আমিও রেডি"
  |  ---- ACK ---------------->  |   "কনফার্ম, শুরু করি"
  |                              |
  |  <====== ডেটা আদান-প্রদান ======>  |
```

### TCP-র প্রধান বৈশিষ্ট্য

- **Connection-oriented:** আগে সংযোগ, তারপর ডেটা
- **Reliable:** হারালে আবার পাঠায় (retransmission)
- **Ordered:** ডেটা ক্রমানুযায়ী পৌঁছায়
- **Flow control:** রিসিভার ধীর হলে প্রেরকের গতি কমায়
- **Congestion control:** নেটওয়ার্ক জ্যাম হলে গতি নিয়ন্ত্রণ করে

### TCP vs UDP

| | TCP | UDP |
|---|---|---|
| নির্ভরযোগ্যতা | বেশি | কম (হারাতে পারে) |
| গতি | তুলনামূলক ধীর | দ্রুত |
| সংযোগ | লাগে (handshake) | লাগে না |
| ব্যবহার | Web (HTTP), Email, File transfer | Video call, Live streaming, Gaming, DNS |

### কোথায় ব্যবহার হয়?

- HTTP/HTTPS (ওয়েবসাইট) — HTTP/1.1 ও HTTP/2 TCP-র উপর চলে
- SSH, FTP, SMTP (ইমেইল)
- PostgreSQL, MySQL, **Redis**-এর সাথে কানেকশন

> **মনে রাখার সূত্র:** TCP = "নিশ্চিত পৌঁছাবে, একটু সময় লাগুক"। UDP = "দ্রুত পাঠাও, দু-একটা হারালে সমস্যা নেই"।

## ২. Redis

### Redis কী?

Redis (**RE**mote **DI**ctionary **S**erver) হলো একটি **ওপেন-সোর্স, ইন-মেমোরি ডেটা স্টোর**। এর ডেটা থাকে **RAM-এ**, তাই এটি অত্যন্ত দ্রুত — সাধারণত মাইক্রোসেকেন্ড থেকে মিলিসেকেন্ড লেভেলে রেসপন্স দেয়।

সহজ ভাষায়: এটা একটা **সুপার-ফাস্ট key-value ডেটাবেস**। তুমি একটা key দিয়ে value রাখো, আবার key দিয়ে value নিয়ে আসো।

### কেন এত দ্রুত?

- ডেটা **RAM-এ** থাকে (ডিস্কের চেয়ে বহুগুণ দ্রুত)
- সিম্পল ডেটা স্ট্রাকচার ব্যবহার করে
- মূল কমান্ড প্রসেসিং **single-threaded**, তাই lock-এর ঝামেলা কম

### বাস্তব উদাহরণ

PostgreSQL যেন একটা বড় লাইব্রেরি — বই খুঁজে পেতে সময় লাগে। Redis যেন তোমার **টেবিলের উপরের নোটপ্যাড** — যে তথ্য বারবার লাগে, সেটা হাতের কাছে লিখে রাখা, তাই এক নিমেষে পাওয়া যায়।

### মৌলিক কমান্ড

```bash
SET user:1:name "Wasim"        # key-value সেট করা
GET user:1:name                # "Wasim" ফেরত আসবে

SET otp:01700000000 "482913" EX 300   # ৩০০ সেকেন্ড (৫ মিনিট) পর নিজে থেকে মুছে যাবে

INCR page:views                # কাউন্টার ১ বাড়ানো
DEL user:1:name                # মুছে ফেলা
```

### Redis-এর ডেটা টাইপ

| টাইপ | বর্ণনা | ব্যবহার |
|---|---|---|
| **String** | সাধারণ টেক্সট/সংখ্যা | ক্যাশ, কাউন্টার, OTP |
| **Hash** | field-value এর সেট (ছোট অবজেক্ট) | User profile, session |
| **List** | ক্রমানুযায়ী তালিকা | Queue, activity feed |
| **Set** | অনন্য মানের সংগ্রহ | Unique visitors, tags |
| **Sorted Set** | স্কোরসহ সাজানো সেট | Leaderboard, ranking |
| **Stream** | লগ-ধরনের ডেটা | Event streaming |

### Redis কোথায় ব্যবহার করবে?

1. **Caching:** ডাটাবেস কোয়েরির রেজাল্ট জমিয়ে রাখা, যাতে বারবার DB-তে না যেতে হয়
2. **Session storage:** লগইন সেশন সংরক্ষণ
3. **Rate limiting:** একটা IP/ইউজার কতবার রিকোয়েস্ট করতে পারবে তা সীমিত করা (যেমন Login brute-force আটকানো)
4. **OTP / টেম্পোরারি ডেটা:** TTL (Time To Live) দিয়ে নির্দিষ্ট সময় পর অটো-ডিলিট
5. **Queue / Pub-Sub:** ব্যাকগ্রাউন্ড জব ও রিয়েলটাইম মেসেজিং (যেমন BullMQ)
6. **Leaderboard:** Sorted Set দিয়ে র‍্যাংকিং

### Cache-Aside প্যাটার্ন (সবচেয়ে প্রচলিত)

```
১. অ্যাপ প্রথমে Redis-এ খোঁজে
২. পেলে → সরাসরি ফেরত দেয়  (Cache Hit ✅)
৩. না পেলে → Database থেকে আনে (Cache Miss ❌)
৪. DB থেকে পাওয়া ডেটা Redis-এ রেখে দেয় (TTL সহ)
৫. পরের বার Redis থেকেই পাওয়া যাবে
```

### Node.js / TypeScript উদাহরণ

```ts
import { createClient } from "redis";

const redis = createClient({ url: "redis://localhost:6379" });
await redis.connect();

async function getProduct(id: string) {
  const cacheKey = `product:${id}`;

  // 1. আগে ক্যাশে খুঁজি
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  // 2. না পেলে DB থেকে আনি
  const product = await prisma.product.findUnique({ where: { id } });

  // 3. ক্যাশে রাখি (৬০ সেকেন্ডের জন্য)
  if (product) {
    await redis.set(cacheKey, JSON.stringify(product), { EX: 60 });
  }
  return product;
}
```

### Persistence (ডেটা কি হারিয়ে যায়?)

RAM-এ থাকে বলে সার্ভার বন্ধ হলে ডেটা যেতে পারে। তাই Redis দুটি পদ্ধতিতে ডিস্কে সেভ রাখতে পারে:

- **RDB:** নির্দিষ্ট সময় পরপর পুরো ডেটার snapshot নেয়
- **AOF (Append Only File):** প্রতিটি write অপারেশন লগ করে রাখে

### সীমাবদ্ধতা

- RAM সীমিত ও ব্যয়বহুল, তাই বিশাল ডেটার জন্য এটি প্রাথমিক ডেটাবেস হিসেবে সাধারণত উপযুক্ত না
- জটিল রিলেশনাল কোয়েরি (JOIN ইত্যাদি) এর কাজ নয়
- মূলত PostgreSQL-এর **বিকল্প নয়, সহযোগী**

> **মনে রাখার সূত্র:** Redis = "RAM-এ রাখা সুপার-ফাস্ট key-value স্টোর", যা ক্যাশ, সেশন, rate limit ও queue-র জন্য দারুণ।

## ৩. gRPC

### gRPC কী?

gRPC (**g**oogle **R**emote **P**rocedure **C**all) হলো Google-এর তৈরি একটি **হাই-পারফরম্যান্স ওপেন-সোর্স RPC ফ্রেমওয়ার্ক**। এর মাধ্যমে একটি সার্ভিস অন্য সার্ভিসের ফাংশনকে এমনভাবে কল করতে পারে, **যেন সেটা নিজের প্রজেক্টেরই লোকাল ফাংশন**।

### RPC মানে কী?

**Remote Procedure Call** = দূরের (অন্য সার্ভারের) একটা ফাংশন কল করা, কিন্তু কোডে লিখতে লাগে সাধারণ ফাংশন কলের মতো।

```ts
// দেখতে লোকাল ফাংশনের মতো, কিন্তু আসলে নেটওয়ার্কের ওপারে অন্য সার্ভারে চলছে
const user = await userService.getUser({ id: "123" });
```

### gRPC কীভাবে কাজ করে?

gRPC-র দুটি মূল ভিত্তি:

1. **HTTP/2** — দ্রুত ট্রান্সপোর্ট (এটি আবার TCP-র উপর চলে)
2. **Protocol Buffers (Protobuf)** — বাইনারি ডেটা ফরম্যাট (JSON-এর চেয়ে ছোট ও দ্রুত)

### Protobuf ফাইল (`.proto`) — চুক্তিপত্র

প্রথমে একটি `.proto` ফাইলে সার্ভিসের "চুক্তি" লেখা হয়:

```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (UserResponse);
}

message GetUserRequest {
  string id = 1;
}

message UserResponse {
  string id = 1;
  string name = 2;
  string email = 3;
}
```

এই ফাইল থেকে **client ও server দুই দিকের কোড অটো-জেনারেট** হয় (TypeScript, Go, Java, Python ইত্যাদি অনেক ভাষায়)। ফলে ভিন্ন ভাষায় লেখা সার্ভিসও একে অপরের সাথে সহজে কথা বলতে পারে।

### গঠন (Flow)

```
[Client Service]                        [Server Service]
 stub.getUser(req)  ──(Protobuf, HTTP/2)──►  getUser(req) চলে
        ◄────────── response ───────────────
```

### gRPC-র ৪ ধরনের যোগাযোগ

| ধরন | বর্ণনা | উদাহরণ |
|---|---|---|
| **Unary** | ১টি request → ১টি response | User তথ্য আনা |
| **Server streaming** | ১টি request → অনেক response | লাইভ স্টক প্রাইস |
| **Client streaming** | অনেক request → ১টি response | বড় ফাইল আপলোড (chunk করে) |
| **Bidirectional streaming** | দুই দিকেই stream | Chat, লাইভ সিঙ্ক |

### gRPC vs REST

| | REST | gRPC |
|---|---|---|
| ডেটা ফরম্যাট | JSON (টেক্সট) | Protobuf (বাইনারি) |
| প্রোটোকল | HTTP/1.1 (সাধারণত) | HTTP/2 |
| গতি | ভালো | অনেক দ্রুত |
| Streaming | সীমিত | বিল্ট-ইন সাপোর্ট |
| ব্রাউজার সাপোর্ট | সরাসরি ✅ | সরাসরি নেই (gRPC-Web লাগে) |
| ডিবাগ করা | সহজ (পড়া যায়) | কঠিন (বাইনারি) |
| Type safety | নিজে ম্যানেজ করতে হয় | `.proto` থেকে অটো |
| সেরা ব্যবহার | পাবলিক API, ওয়েব/মোবাইল ক্লায়েন্ট | মাইক্রোসার্ভিসের ভেতরের যোগাযোগ |

### কখন gRPC ব্যবহার করবে?

- **Microservices** — সার্ভিসগুলোর মধ্যে ইন্টারনাল যোগাযোগ
- যেখানে **কম ল্যাটেন্সি ও বেশি থ্রুপুট** দরকার
- **একাধিক প্রোগ্রামিং ভাষার** সার্ভিস একসাথে কাজ করলে
- **Streaming** দরকার হলে

### কখন REST-ই ভালো?

- সরাসরি ব্রাউজার থেকে কল (সাধারণ ওয়েব অ্যাপ)
- পাবলিক API, যা অন্য ডেভেলপাররা সহজে ব্যবহার করবে
- ছোট প্রজেক্ট, যেখানে সরলতা বেশি জরুরি

> **মনে রাখার সূত্র:** gRPC = "মাইক্রোসার্ভিসের জন্য দ্রুত, টাইপ-সেফ, বাইনারি ফাংশন-কল"।

## ৪. তিনটি একসাথে কীভাবে মেলে?

ধরো একটা e-commerce সিস্টেমে মাইক্রোসার্ভিস আর্কিটেকচার আছে:

```
ব্রাউজার ──(HTTPS/REST)──► API Gateway
                              │
                 ┌────────────┴────────────┐
                 │ gRPC                    │ gRPC
                 ▼                         ▼
          Order Service            Product Service
                 │                         │
                 │                         ├──► Redis (প্রোডাক্ট ক্যাশ)
                 ▼                         ▼
            PostgreSQL                PostgreSQL
```

- **TCP** — এই সবগুলো কানেকশনের **নিচের স্তরে** আছে। ব্রাউজার↔সার্ভার, সার্ভিস↔সার্ভিস, অ্যাপ↔Redis, অ্যাপ↔PostgreSQL, সবই TCP-র উপর চলে।
- **gRPC** — সার্ভিসগুলো একে অপরকে দ্রুত কল করতে ব্যবহার করে (যেমন Order Service → Product Service)।
- **Redis** — বারবার লাগা ডেটা (প্রোডাক্ট লিস্ট, সেশন, rate limit) দ্রুত দেওয়ার জন্য ক্যাশ হিসেবে ব্যবহার হয়।

## ৫. দ্রুত রিভিশন

| | এক লাইনে |
|---|---|
| **TCP** | নির্ভরযোগ্য, ক্রমানুযায়ী ডেটা পরিবহনের নেটওয়ার্ক প্রোটোকল (handshake দিয়ে শুরু) |
| **Redis** | RAM-ভিত্তিক সুপার-ফাস্ট key-value স্টোর — ক্যাশ, সেশন, queue, rate limit |
| **gRPC** | HTTP/2 + Protobuf ভিত্তিক দ্রুত RPC ফ্রেমওয়ার্ক — মাইক্রোসার্ভিসের ইন্টারনাল যোগাযোগ |

### আরও জানার জন্য কী পড়তে পারো

- TCP: OSI/TCP-IP model, TCP vs UDP, TLS handshake
- Redis: TTL, Pub/Sub, BullMQ, Redis Cluster, eviction policy
- gRPC: Protobuf, streaming, interceptors (auth/logging), gRPC-Web, NestJS-এ gRPC microservice
